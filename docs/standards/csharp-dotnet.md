# C# and .NET engineering standard

Use this complete standard for C# source and .NET project/build changes. Rules and examples are inline and usable offline; the source links provide attribution, not missing instructions. Read nearby code, tests, repository instructions and `.editorconfig` first. Explicit repository requirements override these defaults. Apply relevant rules to the requested work; this document does not authorize changes in other files or repositories.

The goal is code a reader can understand without mentally decoding a compressed expression or following trivial helpers. Formatting is necessary but does not establish readability. During cleanup, preserve public signatures, JSON names, defaults, first errors, evaluation order, side effects, cancellation, resource ownership and generated bytes.

## 1. Improve structure, not just whitespace

- Give each method one recognizable operation. Keep orchestration visible: validate, prepare, execute, publish, clean up. Separate unrelated parsing, rendering and publication when that reduces what a reader must hold in mind.
- Extract a helper when its name explains a domain operation or repeated policy. Keep related statements inline if extraction merely hides them. Do not introduce interfaces, factories, managers, service layers or a dependency injection container for a small program's cleanup.
- Replace nested ternaries, nested construction and predicates with branches or named values when they hide distinct decisions. Simple nested value construction is fine when its meaning is clear. A short conditional expression suits two simple values; a switch expression suits a pure mapping.
- Keep mutation and I/O visible as statements. Do not hide assignments, environment reads, file writes or process launches inside queries, property getters or boolean expressions.
- Preserve side-effect order and count. Computing a boolean eagerly is not equivalent to short-circuit evaluation if it reads mutable state, dereferences a nullable object, throws or performs I/O.
- Use guard clauses to expose the normal path, but do not reorder existing guards during cleanup. The first error is observable behavior.

This construction makes the reader decode several decisions together:

```csharp
return new(Get("CONFIG", "product-captures.json"),
    new(Bool("DRY_RUN", true), Bool("REUSE_SCREENSHOTS"),
        Get("URL") is { Length: > 0 } url ? url : null),
    Get("RELEASE_TAG"), Bool("UPDATE_PR"));
```

Use explicit stages. Here `Get` and `Bool` keep their existing parsing/defaults, and reads remain in the same order:

```csharp
string configPath = Get("CONFIG", "product-captures.json");
bool dryRun = Bool("DRY_RUN", true);
bool reuseScreenshots = Bool("REUSE_SCREENSHOTS");
string configuredUrl = Get("URL");
string? url = configuredUrl.Length > 0 ? configuredUrl : null;
var runOptions = new RunOptions(dryRun, reuseScreenshots, url);
string releaseTag = Get("RELEASE_TAG");
bool updatePullRequest = Bool("UPDATE_PR");

return new ActionOptions(configPath, runOptions, releaseTag, updatePullRequest);
```

Name a condition after the decision it represents; keep dependent work after its guard:

```csharp
if (capture is null || reuseScreenshots)
{
    return;
}

bool usesLocalWebHost = capture.Type == "web" && previewUrl is null;
if (usesLocalWebHost)
{
    await StartLocalHostAsync(cancellationToken);
}
```

Do not impose arbitrary method-length, parameter-count or file-length limits. A longer explicit lifecycle can be clearer than several helpers sharing hidden mutable state.

## 2. Name concepts and show useful type information

- Use PascalCase for namespaces, types, members, enum values and constants; camelCase for parameters and locals. Prefix interfaces with `I`. Task-returning operations normally end in `Async`, except established entry points such as `Main`.
- Choose domain names: `outputDirectory`, `configuredUrl`, `needsBrowser`, `cancellationToken`. Avoid unexplained `ap`, `u`, `tmp`, `data`, `helper` or type-encoded names such as `strPath`. Short loop indices and trivial lambda parameters are acceptable.
- Include units/ownership where ambiguous: `timeoutMilliseconds`, `releaseTag`, `sourceDirectory`, `ownedFiles`. Do not rename public or serialized members merely for style.
- Specify accessibility. Use the narrowest useful visibility for new details. Prefer `readonly` for fields not reassigned; use `_camelCase` for new instance fields and respect established static-field naming.
- Use C# aliases such as `string`, `int` and `bool`. Choose numeric types for the domain: normally `int` for counts, `decimal` for exact decimal arithmetic, and explicitly sized types for binary formats/interop.
- Use `var` when construction, a cast or an anonymous projection makes the type apparent. State the type for an opaque method result or a primitive whose meaning matters. A variable name alone does not establish its type.
- Use target-typed `new()` when a nearby declaration states the type. Spell out types in nested construction and ambiguous call arguments. Collection expressions are useful when the target element type is clear and the project supports them.

```csharp
var output = new StringBuilder();
string outputDirectory = ResolveOutputDirectory(config);
TimeSpan timeout = ReadTimeout();
List<string> themes = ["light", "dark"];
Dictionary<string, string> environment = new();
```

## 3. Organize files and layout

- Put `using` directives outside the namespace, `System` imports first, then other imports in the repository's order. Remove unused imports. Prefer a file-scoped namespace for a file containing one namespace.
- Name a file after its principal type. Related small data types may stay together; split files mixing independent responsibilities. Do not add partial classes merely to shorten a file.
- Use four spaces, Allman braces, braced control-flow bodies, one declaration/statement per line, and one blank line between logical groups. Keep simple auto-properties on one line.
- Break long calls, initializers and conditions at logical boundaries. Separate complex arguments and use named arguments when adjacent booleans or numbers are unclear. Do not wrap purely to imitate a documentation site's narrow mobile column.
- Use expression-bodied members for a simple value or transparent delegation. Use a block for branching, mutation, validation, disposal or a multistep calculation.
- Keep project XML readable, normally two spaces and one element per line. Understand MSBuild evaluation order before rearranging elements.

```csharp
public string Name { get; set; } = "";
public string DisplayName => Name;

public void ValidateName()
{
    if (string.IsNullOrWhiteSpace(Name))
    {
        throw new ArgumentException("Name is required.");
    }
}
```

Always-braced bodies are this standard's default, not a universal Microsoft requirement. Runtime and documentation repositories differ in several conventions.

## 4. Model data, construction and nullability deliberately

- Use classes for identity/lifecycle and records for value-like data when generated equality/copy semantics fit. Do not convert an existing class to a record as a cosmetic change.
- Constructors establish valid state. Choose constructor parameters, `required` properties or validated factories according to the existing contract. Do not replace compatible JSON defaults with newly required fields during cleanup.
- Prefer immutable values where practical. Expose read-only collection interfaces when mutation is inappropriate; this does not make the backing collection immutable.
- Use an initializer for related settings and named arguments for otherwise opaque calls. Avoid chains of target-typed `new` expressions hiding the objects being built.
- Enable nullable checking in new projects; change an existing project's context deliberately. Represent absence with `?` and narrow it before dereferencing.
- Do not silence uncertainty with `!` or replace every absent value with `""`. A null-forgiving operator requires a specific established invariant. Preserve null-versus-empty semantics.
- Prefer `TryGetValue`, `TryParse` and patterns for expected absence/invalid input; do not use exceptions as routine lookup results.

```csharp
if (!settings.TryGetValue("theme", out string? theme))
{
    theme = "light";
}

if (capture is not null)
{
    ValidateViewport(capture.Viewport);
}
```

## 5. Make control flow express policy

- Use `&&`/`||` for short-circuit boolean logic; use `&`/`|` when eager boolean evaluation or bitwise work is intended. Parenthesize mixed operators when grouping is unclear.
- Prefer direct branches or a switch to nested conditionals. Keep alternatives together; name a predicate when it explains why a branch exists.
- Avoid repeated expensive parsing/lookups. Capture a result once if behavior is preserved; do not cache mutable state across a point where it can change.
- Preserve `try`/`finally` scopes when moving code. An early return must still clean up everything the operation owns.
- Name meaningful domain constants instead of repeating magic values; do not create constants for every obvious `0` or `1`.

```csharp
string layout = captureKind switch
{
    "obsidian" => "column",
    "quartz" => "column",
    _ => "top"
};
```

## 6. Handle strings and generated formats correctly

- Use interpolation for short text. Use `StringBuilder` for substantial incremental text in loops; do not replace simple concatenation mechanically.
- Raw string literals can clarify multiline embedded text. Verify indentation, newlines and escaping before replacing a literal: generated HTML/JSON, commands and images may depend on exact bytes.
- Use explicit ordinal comparisons for identifiers/protocol values when that matches the contract, and culture-aware comparisons for human-language text. Preserve case sensitivity during cleanup.
- Use invariant culture for machine-readable numbers/dates and the user's culture for presentation. Make encoding/newlines explicit when part of an output contract.
- Escape for the destination: serializers for JSON, HTML encoding for HTML text, URI encoding for URI components. Interpolation is not escaping; prefer structured process arguments over command-string escaping.
- Do not log secrets, tokens or sensitive paths. Errors should name the failed operation and relevant safe context.

```csharp
string opacity = value.ToString(CultureInfo.InvariantCulture);
string label = WebUtility.HtmlEncode(productName);
string message = $"Capture failed for {theme}.";
```

## 7. Use collections and LINQ without hiding work

- Choose lists for order, sets for uniqueness and dictionaries for keyed lookup. Specify a string comparer when key comparison is policy.
- Use LINQ for clear filtering/projection; use a loop for mutation, I/O, early exit or several dependent steps. Keep predicates/projections free of side effects.
- Use `Any` for existence rather than counting everything. Avoid repeated enumeration of deferred or one-shot sequences. Materialize once when a stable snapshot or multiple traversals are needed, not indiscriminately.
- Preserve iteration order and enumeration timing, particularly around exceptions, files and database queries. Moving an operation from `IQueryable` to `IEnumerable` may move execution from a provider to memory.
- Name nontrivial query variables meaningfully and disambiguate projected fields. Prefer `customerName` and `supplierName` over two ambiguous `Name` values.

```csharp
string[] missingFiles = requiredFiles
    .Where(path => !existingFiles.Contains(path))
    .ToArray();

foreach (string path in missingFiles)
{
    ReportMissingFile(path);
}
```

Here `existingFiles` is an already captured set, so the query performs no filesystem I/O. `ToArray()` snapshots the selection before reporting; this matters if later work changes the collections.

## 8. Use delegates, events and comments with purpose

- Prefer `Func<...>`/`Action<...>` for small callbacks. Define a delegate/event type when it communicates a useful public contract.
- Use a lambda for a small inline operation, a named method/local function for branching, repeated use or a domain concept. An async lambda passed as `Action` becomes `async void`; match the actual callback contract.
- Unsubscribe from longer-lived publishers when the subscriber's lifetime ends. Retain the handler when removal is needed; do not capture disposable short-lived state in callbacks that outlive it.
- Explain non-obvious constraints, algorithms and ownership with comments. Prefer clear code to comments restating statements. Keep longer rationale in documentation where appropriate.
- Write XML documentation for externally consumed APIs when behavior, exceptions or ownership need explanation. Do not generate ritual documentation for every private helper.

## 9. Make async work, cancellation and ownership explicit

- Use native async APIs for I/O; do not wrap synchronous I/O in `Task.Run` to appear asynchronous. Offload CPU work only when measurement and the caller's needs justify it.
- Await owned tasks. Avoid `.Result`, `.Wait()` and `.GetAwaiter().GetResult()` on async paths. Reserve `async void` for required event contracts, with failure handling at that boundary.
- Pass the operation's cancellation token through supporting APIs, normally as the last parameter. Do not replace it with `None` or create unrelated cancellation in a helper.
- Keep token sources/registrations alive for the operation and dispose afterward. Preserve the distinction between timeout, requested cancellation and failure.
- A token does not cancel an API that ignores it. Preserve the established interruption/cleanup mechanism for such dependencies and report limits honestly.
- Use `using`/`await using` for resources owned by the scope; never dispose borrowed dependencies. Use `finally` for cleanup not represented by disposal. Preserve success/failure/cancellation cleanup.
- Use `Task.WhenAll` for independent operations, observe all owned tasks and bound concurrency where resources can be exhausted. Do not parallelize ordered validation or publication.
- Follow the library's synchronization-context policy for `ConfigureAwait`; do not add/remove it as a style ritual.

```csharp
await using FileStream output = File.Create(destination);
await source.CopyToAsync(output, cancellationToken);
```

## 10. Preserve failure causes and recover deliberately

- Throw a specific exception for a failed contract. Use `nameof` for parameter-name arguments. Preserve existing exception type/message/order during behavior-preserving cleanup.
- Catch where recovery or useful boundary reporting is possible. A top-level CLI catch returning failure can be appropriate; a helper swallowing every failure and reporting success is not.
- Rethrow with `throw;` to preserve the stack. Keep an inner exception when translating meaningfully; do not log and rethrow redundantly at every layer.
- Do not hide cancellation in a broad catch or classify every error as cancellation merely because a token is requested. Preserve the existing caller contract.
- Restore partial changes when rollback is promised. If cleanup also fails, keep the original failure visible according to the project's diagnostic policy.

```csharp
catch (IOException error)
{
    throw new InvalidOperationException("Capture input could not be loaded.", error);
}
```

Translate an exception only at a boundary where the operation context benefits the caller; otherwise let the original propagate. The inner exception above retains the I/O cause. Do not introduce a new exception type during a cleanup that promises unchanged errors.

## 11. Respect configuration, filesystem and process boundaries

- Validate untrusted input before side effects. Preserve omitted/null/empty/invalid distinctions instead of silently converting malformed input into a default.
- Preserve JSON names, serializer settings, defaults, accepted variants and rejection behavior. Keep data and derived runtime state distinct when the existing model supports it; do not change a schema to tidy internals.
- Use `Path` and `Uri` APIs for their domains. Reuse verified path-containment logic and account for the application's symlink policy; a string-prefix check alone is insufficient.
- Use `ProcessStartInfo.ArgumentList` for structured executable arguments. Invoke a shell only when shell syntax is an intentional command contract, with an explicit trust boundary.
- Drain redirected stdout/stderr concurrently to avoid full-pipe deadlock. Observe startup errors, exit status, timeout and cancellation. Stop owned descendants and await cleanup under the existing lifecycle policy.
- Retry only classified transient operations with a bound and cancellation. Do not retry mutation/publication unless idempotency is established.
- Change only owned output files. Stage/validate before replacement where promised; preserve unrelated files. Do not claim multi-file replacement is crash-atomic without evidence.

## 12. Keep projects and dependencies simple

- Stay within the supported SDK, target framework and language version. Do not silently upgrade or set `LangVersion` to `latest` to use a new feature.
- Follow existing package/version/lock-file management. Add dependencies for requested capabilities with concrete benefit, never solely for style.
- Reuse shared properties/utilities; introduce a project or central build file only for a real shared need. Preserve MSBuild ordering and conditions.
- Scope analyzer changes deliberately. Do not hide new problems with `NoWarn`, lowered severity or broad suppressions. Report environmental restore/audit failures accurately.
- Apply ASP.NET, UI, persistence, DI and cloud guidance only when that technology is actually relevant. No such framework is required by this general standard.

## 13. Verify behavior and review in separate passes

Before cleanup, state the smell, the simpler intended structure and contracts to preserve. Read callers/tests. Add a regression first for an uncovered behavior-sensitive boundary; do not test formatting or private helper names.

Test observable results deterministically and in isolation: inputs/defaults, first failure, cancellation, ownership, rollback and exit status where relevant. Preserve fixtures and unrelated dirty work. Compare bytes when generated text or approved visuals are contracts. Do not refresh snapshots merely to make a refactor pass.

1. **Behavior:** Check contracts, evaluation order, side effects, lifetimes and failure paths; run targeted regressions first.
2. **Structure:** Verify that dense expressions/mixed responsibilities are actually simpler. Extraction should reduce cognitive load, not merely increase navigation.
3. **Style:** Check names, type clarity, braces, layout, imports and comments. Format only the authorized scope.
4. **Evidence:** Build with configured analyzers, run relevant tests, verify outputs and inspect the final diff. Report checks and gaps; formatting success is not structural approval.

Typical SDK-style commands, using the repository's actual project paths and runner:

```sh
dotnet restore path/to/Project.csproj
dotnet format path/to/Project.csproj --verify-no-changes --no-restore
dotnet build path/to/Project.csproj --no-restore
dotnet test path/to/Tests.csproj --no-restore
```

Some projects use executable contracts instead of `dotnet test`; run their documented commands. Formatting/SDK analyzers enforce only configured diagnostics. They cannot prove cohesive responsibilities, good domain names, ownership or equivalence. `EnforceCodeStyleInBuild` does not turn every IDE diagnostic into a build error; configure severity and use formatter verification for the supported subset.

For structural, behavior-preserving C# cleanup, use the official `csharp-refactoring` skill when available. It supplements the behavior/structure review; it does not replace this standard, guarantee enforcement or become a prerequisite for normal edits. The standard remains usable without any plugin.
